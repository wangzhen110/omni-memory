## 2. 【核心纠错】文本表 48.09% 不是 index.js 的真实覆盖率

| 证据 | 数值 |
|---|---|
| LCOV 中 `index.js` 被记录次数 | **447**（4.6.6 为 446），每条 LF=603 |
| 文本表 48.09% 来源 | 取了**一条代表记录**：LH=290/603，277 条记录的 LH 都是 290（众数），全部 447 条 LH 范围 259~380 |
| `all files 53.25%` 来源 | 不去重求和把 447 份 index.js 的 LF 直接累加，虚增分母 |
| **DA 行并集** | **586/603 = 97.18%** ← 真实行覆盖 |

`all files 53.25%` 与逐文件 `index.js 48.09%` 是**同一个根因的两种表现**：前者虚增分母，后者只显示一条代表记录。4.6.6 报告只发现了前一种，漏掉了后一种。

三段补测区间在并集下**全部命中**：

| 区间 | 内容 | 并集命中 |
|---|---|---|
| 335-394 | readJsonBody 安全边界 | **60/60 (100%)** |
| 531-570 | prompt 注入预算裁剪 | **40/40 (100%)** |
| 582-594 | 后台租约 | **13/13 (100%)** |

交叉印证：新测试 `test/entry-body-4.6.7.test.mjs`、`test/prompt-and-dream-4.6.7.test.mjs` 直接 import `index.js` 导出函数并逐条断言行为；若判这三段"未覆盖"，等于说这些真实调用不算数。

### 2.1 分支并集的方法学分歧（已裁决）

三种算法的结果不同，根因是 LCOV 的 `BRDA:line,block,branch,taken` 里 branch index **恒为 0**（实测全部 24,653 条都是 0），真正区分分支的是 `block`；而 `block` 在每条记录内部是 0..BRF−1 的顺序编号，**跨记录随进程加载了哪些函数而重新编号**（同一行 582 出现 53 个不同 block id）。

| 算法 | 结果 | 判定 |
|---|---|---|
| A `(line,block,branch)` 全三元组 | 747/1678 = 44.52% | ❌ **无效测量，不是分歧的一端**：把跨记录被重编号的同一分支当成不同分支，分母虚高 9 倍；不可用于验收判断 |
| B `(line,branch)` 忽略 block | 117/186 = 62.90% | ✅ 有效下界：因 branch 恒 0 等价于按行去重，保守 |
| **F `(line,行内第N个分支)`** | **158/246 = 64.23%** | ✅ **推荐值**：block 在记录内按源码顺序递增，行内序号跨记录稳定，最忠实 |

**有效区间 62.90% ~ 64.23%，两种有效算法都 ≥ 55%**——P0-1 的分支验收判定**不受方法选择影响**。44.52% 是无效测量，不构成"另一个答案"。每行分支数分布：144 行×1、26 行×2、14 行×3、2 行×4，两侧独立复现一致。

### 2.2 对 4.6.6 基线的影响（需加限制说明）

> **`index.js 47.84%`（以及据此得出的"314 行未覆盖""入口合计 773 行未覆盖""30 模块 87.77%"）受 Node 22 文本表单条记录口径限制**：该模块在 LCOV 中被 446 个测试子进程重复记录，文本表仅显示其中一条代表记录；并集口径下真实行覆盖远高于此值。**该数字只能用于同口径的迭代间趋势对比，不能用来衡量该模块真实覆盖水平或作为"未覆盖行数"的依据。**

这不是说 4.6.6 的方向判断错了——当时测试确实没驱动那些函数，入口层是补测重点的判断依然成立——而是**数字本身被工具口径压缩了**。
