## 3. 重要项详述

### I-1 「产物来自发布提交」的措辞失实（不阻断，但必须改）

**实测链路**（`install.mjs:180-197`、`install-launcher.mjs:155-166`）：

1. `verifyOfficialRelease()` 验签官方 Release，返回 `release` 对象；
2. `main()` 调 `installLauncherFromCommit({ commit })`，传的是 CLI `--commit`（`npm run setup` 未传 → `undefined`），不是 `release.commit`；
3. `installLauncherFromCommit` 内 `commit = options.commit || git rev-parse HEAD` → **从 HEAD 读 `package.json` 和 launcher 字节**；
4. `gitShow(HEAD:package.json).omni.launcher.sha256` 与 `gitShow(HEAD:<launcher>)` 直比——这是**同提交自洽校验**，不是与签名 manifest 的 `launcherSha256` 直比；
5. 签名 manifest 里的 `packageJsonSha256` / `launcherSha256` 只在 `verifyRelease()` 内校验**远端 signed.commit 的对象**，从未参与本地落盘字节比对。

**影响**：当前 HEAD 是 docs-only 后代，diff 零源码改动，所以落盘字节**确实等于**发布提交——结果正确。但 `install.mjs:142` 打印的「启动器校验: Release manifest v2 Ed25519 + 签名 commit SHA-256」名不副实：整个安全链押在 `describeHeadDelta` 这一个判定点上，没有第二道字节级绑定。DESIGN §6.22 与汇总 §5 都把「机制保证」写成了「来源事实」。

**建议**：要么让安装器用 `release.commit` 读对象（或把 `release.launcherSha256` 传入直比落盘字节），二选一；要么把 DESIGN/汇总措辞改为「HEAD 与发布提交的差异仅限 docs/，故字节等价；签名哈希校验的是发布提交对象」。前者是加固，后者是诚实表述，**最小改动选后者**。

### I-2 云主机证据时钟倒挂

`docs/evidence/4.6.9-vm.txt:5` 写「采集时间: 2026-11-27 10:34 +0800（本地）」，但该文件 mtime 是 `10:19:05`、由 `185da7d`（10:19:13 +0800）提交——**声称采集时间比落盘和提交都晚约 15 分钟，物理不可能**。

对照：4.6.8 的同型文件写 09:44、mtime 09:49:19、提交 09:50:09，采集 < 落盘 < 提交，自洽。所以这是 **4.6.9 新增错，不是重复犯错**。

数字本身（545/542/0/3）与文件内 TAP 摘要一致，但该文件自述「是摘要，不是完整 TAP」，证据等级低于本地原始 TAP。建议把采集时间改为不晚于 10:19:05 的实际值，并注明云主机 TAP 原始日志路径（现写 `/tmp/vm469.log`，本地不可查）。

## 4. 主理人裁决与认账

1. **安全路两条"重要"，一条维持、一条降级**：I-1 维持重要（措辞掩盖了单点依赖，属安全模型表述失实）；`GIT_BIN` 劫持降为建议 S-6——`git log -S'GIT_BIN'` 证明它来自 v3.11.8/v4.0.0，本轮 `6b78ad5` 对 `install.mjs` 只加了放行判定，没有扩散这个风险；且利用前置是能设置 setup 进程环境变量的本地攻击者，本就不属于远程威胁面。
2. **覆盖率归因（S-2）**：我实测确认数字属实，也确认归因无据——`git show 6b78ad5 --name-only` 无 `hosts/mcp/server.mjs`，触达它的 stdio 测试也全部未改；只有两份 lcov、零同提交重跑对照。121-132 是 `createProtocol.handle()` 的 prompts/list 分支，由 `mcp.test.mjs:137` 确定性调用，用「分支子集波动」解释尤其站不住；154/165 所在的 fuzz 用例确为无种子 fast-check，可作**合理推断**但未经证实。措辞应改为「差异来自测试运行（源码未变），具体触发用例未逐次对照」。
3. **我给评审团的提问里有措辞错**：我写了「DESIGN §6.22 与汇总 §5 五条是否一一对应」——汇总 §5 实际是 4 条、DESIGN §6.22 是 3 条加引导语，我凭印象写了"五条"。评审团据此回了一条"计数有误"，经核**不成立**，不列入问题清单。认账。
4. **前几轮报告的历史教训继续有效**：不用 commit 对象时间戳当源码落盘时刻；tag object 本地/远端不一致先查 `git ls-remote`；`verify-release` 只优先读 v2，v1 必须人工逐份回读（本轮卫不漏已做）。
